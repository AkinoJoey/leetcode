Binary Search テンプレート

初出：Lesson 14。迷ったらここに戻る。

1. 前提（⓪）

  • ソート済みであること。保証しているのは問題文か、自分の sort() か——毎回どちらかを言う。
  • 自分でソートするなら O(n log n) に飲まれる。探索が1回だけなら、線形探索と変わらない。元が取れるのは探索が何度も走るとき。
  • 「ソート済み」でなくてもよい場合がある：判定が単調（ある境界より前は全部 False、後は全部 True）なら二分探索できる。配列でなくてもよい（答えの値域を二分する）。

2. 不変条件（③の主語）

答えが存在するなら、それは常に [left, right] の中にある。

③ を書く手順は two pointers と同じ：先に消える区間を名指し、次に理由。

  • 名指し：「捨てるのは left..mid の区間です」
  • 理由：「ソート順より、そこは全部 target 未満だからです」

「小さいほうを動かします」は②（手順）であって③（理由）ではない。

3. 型 A：厳密一致（704 型）

def search(nums, target):
    left, right = 0, len(nums) - 1     # 閉区間 [left, right]
    while left <= right:
        mid = (left + right) // 2
        if nums[mid] == target:
            return mid
        if nums[mid] < target:
            left = mid + 1
        else:
            right = mid - 1
    return -1

三つの決め事は連動する

区間の取り方while更新
[left, right] 閉区間left <= rightmid + 1 / mid - 1
[left, right) 半開区間left < rightmid + 1 / mid
[left, right] 閉区間left <= rightmid（±1 なし）→ 無限ループ

一つ変えたら三つとも見直す。閉区間で left = mid と書くと、 left=3, right=4 で mid = 3、left が動かず止まらない。

提出前チェック（必ず手で回す）

要素が2つ隣り合った状態（right == left + 1）で1周させ、 範囲が真に狭まるかを確かめる。二分探索のバグはほぼ全部ここに出る。

4. 型 B：境界を探す（lower / upper bound）

面接で本当によく出るのはこちら。「条件を満たす最小の添字」を返す形。 == で早期 return せず、最後まで詰めるのが型 A との違い。 

def lower_bound(nums, target):
    """nums[i] >= target となる最小の i。無ければ len(nums)。"""
    left, right = 0, len(nums)          # 半開区間 [left, right)
    while left < right:
        mid = (left + right) // 2
        if nums[mid] < target:
            left = mid + 1              # mid は条件を満たさない → 捨てる
        else:
            right = mid                 # mid は候補として残す
    return left                         # left == right が答え
  • right = mid であって mid - 1 ではない。mid 自身がまだ答えの候補だから。
  • 返すのは left。ループを抜けた時点で left == right、そこが境界。
  • < を <= に変えると upper bound（> target となる最小の添字）になる。

標準ライブラリの bisect_left / bisect_right がこれそのもの。ドキュメントの保証： bisect_left の返り値 ip について a[lo:ip] は全部 < x、a[ip:hi] は全部 >= x。 リストがソート済みであることは確認しない（"assuming that a is already sorted"）——前提は呼び出し側の責任。 

from bisect import bisect_left, bisect_right

i = bisect_left(nums, x)                  # x を挿入できる最も左の位置
found = i < len(nums) and nums[i] == x    # 存在判定はこの一行が必要
cnt = bisect_right(nums, x) - bisect_left(nums, x)   # x の個数

±1 が付くかは、左右では決まらない

「左は +1、右は無し」と位置で覚えると型が変わった瞬間に崩れる。 判定基準はひとつだけ——その枝で mid が候補として生き残るか。

その枝で mid について分かったことmid は候補か更新
答えではないと確定した消えるmid ± 1（候補から外す）
答えかもしれない残るmid（±1 を付けない）

③で「mid はまだ候補」と書いたなら、コードは right = mid になる。 ③とコードは直結している——③が書けていれば ±1 で迷う余地はない。

配列が無い型（述語ベース・278 型）

二分探索に必要なのは配列ではなく単調性。真偽が ✗ ✗ ✗ ✓ ✓ ✓ と並び、一度 ✓ になったら ✗ に戻らない——これだけあればよい。 ⓪では「ソート済み」ではなく、何が、どういう意味で単調かを書く。 

def first_true(lo, hi, pred):
    """pred(i) が True となる最小の i。pred は単調（False…False True…True）。"""
    while lo < hi:
        mid = (lo + hi) // 2
        if pred(mid):
            hi = mid                # mid は「最初の True」かもしれない → 残す
        else:
            lo = mid + 1            # mid は False と確定 → 消す
    return lo
述語ベース特有の落とし穴：図に描いた ✗ は、まだ呼んでいない

配列問題（35 など）では値が最初から全部見えているので、 ✗ ✗ ✓ ✓ ✓ の図をそのまま根拠に使ってよかった。 述語ベースでは、呼んだ 1 点以外はすべて未知。 

version    1    2    3    4    5    6
真の姿      ✗    ✗    ✗    ✓    ✓    ✓     ← 説明用の図。プログラムには見えない
判明        ?    ?    ?    ✓    ?    ?     ← mid=4 を呼んだ直後に知っていること

③の根拠に使ってよいのは 下の行だけ。 「1,2,3 は ✗ だから消せる」はまだ呼んでいない情報を使っている。 消えるのは 5..n の側——単調性より必ず bad だが、4 が既に bad なので「最初」ではありえない。

5. 型 C：回転済みソート配列（33 / 153 型）

⓪は「ソート済み」ではない。どこか1点に切れ目があり、切れ目を含まない側は必ずソート済み。 毎周まずどちらの半分がソート済みかを判定し、 ソート済みの側だけが両端＝下限と上限を与えてくれるので、そこで target の有無を決める。 

def search(nums, target):
    l, r = 0, len(nums) - 1
    while l <= r:
        mid = (l + r) // 2
        if nums[mid] == target:
            return mid
        if nums[l] <= nums[mid]:                 # 左半分 [l, mid] がソート済み
            if nums[l] <= target < nums[mid]:    # 左に「ある」条件
                r = mid - 1
            else:
                l = mid + 1
        else:                                     # 右半分 [mid, r] がソート済み
            if nums[mid] < target <= nums[r]:    # 右に「ある」条件
                l = mid + 1
            else:
                r = mid - 1
    return -1

③は、枝ごとに書く。「もう一方も同じ」では書けていない

分岐が対称に見えても、③を片側だけ書くと書いていない側だけが壊れる （LR-0024）。 主語の区間も条件の向きも両方反転するので、2欄そろえて書く。

左枝（nums[l] <= nums[mid]）右枝（else）
ソート済みなのは[l, mid][mid, r]
成り立っている事実nums[l] <= nums[mid]nums[mid] <= nums[r]
下限を与えるのはnums[l]nums[mid]
上限を与えるのはnums[mid]nums[r]
「ここにある」条件nums[l] <= target < nums[mid]nums[mid] < target <= nums[r]
提出前チェック：③に書いた事実と、条件式が矛盾していないか

右枝で nums[mid] > target > nums[r] と書くと、nums[mid] > nums[r] を要求することになる。 しかし右枝に入った時点で nums[mid] <= nums[r] が成り立っている—— この条件は恒偽で、右半分を一度も見ない。テストの不一致は約4割に出る。

バグではなく説明と実装の論理矛盾なので、③を読み返せば実行前に見つかる。 ③に「両端が下限と上限を与える」と書いてあるなら、 下限側の変数と上限側の変数が式の中で入れ替わっていないかだけ確認する。

誤正症状
nums[l] < target < nums[mid]nums[l] <= target < nums[mid]区間の左端にある target を落とす
nums[mid] > target > nums[r]nums[mid] < target <= nums[r]恒偽。右半分を一度も見ない
if nums[l] < nums[mid]if nums[l] <= nums[mid]l == mid（残り2要素）で else に落ち、前提が壊れる
a・b は条件式の誤り。c だけは前提の誤り

if の行は候補を消す行ではなく、③の前提（どちらがソート済みか）を作る行。 等号を落とすと、l == mid（＝ nums[l] == nums[mid]、左は1要素なので当然ソート済み）のケースを 「右がソート済み」という偽の前提で書かれた枝に送り込む。 

残り区間 [2, 1]、target = 1
mid = l なので nums[l] == nums[mid] == 2
  <  なら → else へ。だが右半分 [2, 1] はソート済みではない（ここに切れ目がある）
            条件式 nums[mid] < target <= nums[r] は 2 < 1 <= 1 で偽 → r = mid - 1
            → 右端の 1 を捨てて -1 を返す
  <= なら → 左枝へ。nums[l] <= target < nums[mid] は 2 <= 1 で偽 → l = mid + 1 → 1 に到達

残り1要素でも else に落ちるが、そちらは安全（[mid, r] が1要素なのでソート済みは真、かつ nums[mid] == target は先頭で弾いてある）。壊れるのはちょうど2要素のときだけ—— だから乱択テストでは末端でだけ再現し、目でも見つけにくい。

最小値を探す（153）は型Cではなく first_true そのもの。 述語は「nums[i] <= nums[-1]」——切れ目より後ろで初めて真になる単調な述語。 枝が1つなので上の2欄表は要らない。型Cを使うのは target を探すときだけ。

6. 計算量（⑥）の言い方

毎回、残っている範囲の半分を捨てる。n → n/2 → n/4 → … → 1 なので n / 2^k = 1、すなわち k = log₂ n 回。よって O(log n)。空間は O(1)。
  • 「ソート済みだから log n」は誤り。ソート済みは捨てる権利を与えるだけで、速さを与えない （two pointers も同じ前提で O(n)）。log を生むのは率。
  • log が出る場所は常に「何回で 1 になるか」を数えたとき。
  • 再帰で書くと空間は O(log n)（スタック）。反復なら O(1)——書き方で変わるので言い分ける。
  • 自分で sort() したなら O(n log n)。1行目から数える （Lesson 13）。
  • 「半分にできる」ではなく「毎回必ず半分になる」。 更新行は条件分岐のどちらを通っても実行されるので、可能性ではなく確定。

言った率を、行で名指しする

⓪で使っている形（前提と、それを保証している行の名指し。名指しできなければ、その行はまだ存在しない）を そのまま⑥に適用します。

⑥で「毎回 X 捨てる」と言ったら、X を実現している行を指す。指せなければ、その行はまだ存在しない。
⑥で言ったことそれを実現している行実際の計算量
毎回 半分捨てるleft = mid + 1 / right = mid - 1O(log n)
毎回 半分捨てる（と言ったが）left += 1 / right -= 1O(n)。主張と実装が別物
落ちないバグ

テストは通ります。left += 1 でも target を範囲の外に出さないので、 答えは正しく返り、テストは通ります。遅いことだけが残る。 ③が保証しているのは「mid+1 まで進めてよい」であって、進めなければならないとは言っていません ——正しさは率を強制しない。 16 の sort() 欠落（LR-0015）と同じ構造です。
