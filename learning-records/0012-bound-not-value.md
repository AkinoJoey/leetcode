# 11 完答。③は「値を知る」から「上限を押さえる」への転換で越えた

11 Container With Most Water を完答。ただし到達までに**7往復**を要した。
sliding window（424・1004）が1〜2往復だったことを考えると、ここが現在の最難関だった。

## 詰まりの連鎖（すべて別種）

1. **問題文が読めない**（「間の柱は無視する」が分からない）→ 図とルール3点で解消。
   これは能力の問題ではなく 11 の問題文が悪い。①問題の確認＝面接では質問してよい場所、と接続した。
2. **「ソート済みでないから捨てられない」**（最大の壁）。167 から
   「③にはソートが必要」と過剰般化していた。[[0011-discard-rate-vs-discard-reason]] と同型
   ——**例の付随的特徴が概念に貼り付く**。
3. **「捨てる」の対象を取り違え**：「l=0, r=8 が最大かもしれないのに捨ててよいのか」。
   計算済みペアと未計算ペアの区別がついていなかった。**`left += 1` が何を消すのか**を
   ペア空間（36通り中の1行）で示して解消。
4. **③を167の文面で使い回した**（`target`→`最大値` の置換のみ、水位も幅も入っていない）。
5. **③の適用条件を抽出していなかった**：③を `h[0]` という具体例で書いたため、
   「捨てるのは**低いほう**」が落ち、コードが `left += 1` 無条件になった。

## 核心（3の解消がすべてを開けた）

> **③は個々の値を知ることではなく、上限を押さえること。**

11 で上限をくれるのは `min` と添字であって、ソートではない。`h[j]` は最後まで一度も要らない
（幅は `j - l < r - l`＝添字だけ、水位は `min(h[l], h[j]) ≤ h[l]`＝min の性質）。
167 でソートが要ったのは「和の上限を得る手段がソートしかなかった」から。
**ソートは③の必須条件ではなく、上限を得る手段のひとつ。**この対比で「ソートがないと捨てられない」が崩れた。

さらに、③が主張しているのは「捨てた中に良いものがない」ではなく、より弱い
**「捨てたものは*すでに計算した値*を超えられない」**。比較の基準が手元の `best` であることも明示が要った。

## Implications

- **③は「例で書かせない」。**具体例で書くと適用条件（＝どちらを捨てるか）が文面から消え、
  コードの分岐に落ちない。③は**最初から一般形（「低いほうの柱」）で書かせる**こと。
  今回、③の具体例化とコードのバグは**同一の欠落**だった。
- 逆に言えば、**③が正しく書ければコードの分岐は自動的に決まる**。この対応関係は次問で明示的に確認する。
- `≤` と `<` の区別は指摘1回で正確に入った（水位 ≤ / 幅 <、面積が厳密に小さいのは幅のおかげ）。
  [[0004-off-by-one-dominant]] 以降の境界精度は安定して高い。
- 定型文（穴埋め）は**形は与えるが中身を保証しない**。167 の定型文をそのまま流用されたのがその証拠。
  枠の有効性（[[0009-rubric-fixed-explanation]]）には限界がある——
  **枠が問題固有の量を要求する形になっていないと、空虚に埋まる。**
  今回効いたのは定型文ではなく「問1=幅／問2=水位／問3=面積」と**問題固有の量を先に個別に問う**やり方。

## 別件：説明の指摘が反映されない（要観察）

コードのバグ指摘は1往復で直った。一方、docstring への指摘（`[空間1]` を `-` にしない、
②の「再計算」欄が11に合っていない）は**2往復とも反映されなかった**。
[[0008-explanation-lags-implementation]] の再発だが、今回は「気づけない」ではなく
**「指摘されても直さない」**という別の形。ミッション上は説明のほうが配点が高いので、次回冒頭で一度だけ明示する。

## 別件：`⚠` の使い方

3回連続で `left < right` を挙げた。167 で解決済みなので、もう最弱点ではない。
11 で議論の余地があるのは `if height[left] < height[right]`（同値時にどちらを動かすか）。
**`⚠` は毎回その問題固有の行を指させる**。この欄は3回的中しており、最も機能している装置なので摩耗させない。
