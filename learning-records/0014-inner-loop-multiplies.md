# 15 未完。自己検算式が誤りを通した（介入の失敗）／`break` は 167 の持ち込み

15. 3Sum。**骨格は完全に正しい**（sort → i 固定 → 両端で挟む＝標準解そのもの）。
パターン選択・境界・③の形式はすべて通過。落ちたのは2点で、**どちらも同じ見落とし**から出ている。

## 検証結果

`break` により解を取りこぼす。実行で確認：

```
[-3,-1,0,1,2,3] → (-3,1,2) が欠落
[-2,0,1,1,2]    → (-2,1,1) が欠落
```

取りこぼしは常に**「同じ i に対する2組目以降」**に出る。LeetCode の例
（`[-1,0,1,2,-1,-4]`）ではこれが起きないため、手元テストでは気づけない入力だった。

## 中心：内側ループは「足し算」か「掛け算」か

⑥は `[時間1] n回 / [時間2] O(1) / [時間3] O(n) → O(n)` と誤答。

**重要なのは、[[0013-two-kinds-of-discard]] で導入した自己検算式がこの誤りを検出しなかったこと。**

```
[時間1] × [時間2] + [時間3] = n × O(1) + O(n) = O(n)   ← 結論と一致してしまう
```

学習者は検算を正しく実行しても誤りに到達できない。**検算式のほうが不完全だった**（教材の欠陥）。
`+ [時間3]` が許されるのは**償却できるとき**、すなわち内側ポインタが外側の反復をまたいで
生き残るときだけ。15 は `j,k = i+1, n-1` で毎回リセットされるので掛け算になる。

| 内側ポインタ | 数え方 | 例 |
|---|---|---|
| 持ち越される（戻らない） | **足し算**（償却） | 424, 3 |
| リセットされる | **掛け算** | 15, 16, 18 |

→ `[時間3]` の欄を「回るとは限らない内側ループ（償却）」から
**「持ち越しかリセットかを明記する」**欄に変更（`interview-protocol.html`）。
**数字だけ書かせると、この区別が欄から消える**——欄名が償却を前提していたのが直接の原因。

## 統一フレーム：15 は「167 を n 回解く」帰着

`i` を固定すれば、残りは「和が `-nums[i]` のペアを探す」＝ 167 そのもの。この見方から**両方の誤りが同時に落ちる**：

- コスト = n × (167 のコスト) = **掛け算**
- `break` = **部分問題を解ききっていない**。167 は「解は1つ、見つけたら return」だが 15 は全部列挙。
  → **内側ループの止め方は、外側の問題文が決める。**

`break` は無知ではなく **167 の文面の持ち込み**。NOTES の「前問の文面をそのまま持ち込む癖」が
docstring だけでなく**コードでも起きた**のは初めて。[[0011-discard-rate-vs-discard-reason]]
（例の付随的特徴が概念に貼り付く）と同型。

## 空間欄の自己矛盾（新規の型）

```
[空間2] 入りうる最大の要素数は: O(1)
[空間3] 入力サイズに依存するか: する      ← [空間2] と矛盾
→ 空間: O(1)
```

`[空間2]` と `[空間3]` は**同じことを二度聞いている**（定数個 ⟺ 依存しない）。
片方を過去問から流用すると、ここで必ずねじれる。**枠の中での整合チェック**を rubric に追加した。
[[0009-rubric-fixed-explanation]] の「枠は埋まるが中身は保証しない」の別形——
**枠が複数あると、埋まった枠同士が矛盾していても気づかれない。**

`nums.sort()` の計上漏れも同種（自分で書いた操作が⑥に現れない）。
[[0013-two-kinds-of-discard]] の「主張と実装の不一致」の再発。

## 良かった点

- **③が形式チェックを通過**（「〜ない」で終わる否定文）。3往復を要した 125 からの明確な改善。
  残るのは3段目が結論だけの点だが、型としては定着。
- **`⚠` が5回連続で的中**：`for i in range(len(nums))`。まさに `break` と重複スキップの所在。
  この欄は最も機能している装置。摩耗させない。
- 骨格・ソートの必要性・両端の初期化はすべて自力。**two pointers の型そのものは獲得済み。**

## Implications

- 教材に**償却を前提した欄名**を置いたことが誤りを誘導した。
  NOTES の「抽象化した箇所がその問題の難所」の変種：**欄名に埋め込んだ前提も同じ罠になる。**
- 検算式は「矛盾が自動的に出る手続き」として正しい方向だが、**前提条件付きの式は前提ごと渡す**必要がある。
- 次の検証点：16. 3Sum Closest で（a）`[時間3]` に掛け算と書けるか、（b）target 一致時に
  `return` してよいかを外側の問題文から判断できるか。
