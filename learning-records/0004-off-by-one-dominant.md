# 詰まりの主因はオフバイワンに一本化された

2026-07-19 の1セッション内で、境界のオフバイワンが3回発生した。

1. `range(len(prices), 0, -1)` — 初回で IndexError、かつ添字0に到達しない
2. `right - left + 1` の +1 が要る理由が曖昧（クイズでは正答したが説明は出なかった）
3. `range(k+1)` で初期窓を k+1 個ぶん合計（2箇所、同一セッション内で再発）

**Evidence:** 一方で、アルゴリズム面では一度も詰まっていない。
Lesson 02 の中核概念（`left` の単調性、固定長窓の左端を `right - k` で導出）は、
問いを1つ投げれば自力で到達した。**概念 ≫ 境界**という非対称がはっきりした。

**Implications:**
- 教える対象を切り替える。パターンの説明に時間を割くより、**境界の検証習慣**を作るほうが投資効率が高い。
- 与えた道具：**境界は推論せず、小さい具体値を代入して数える**（k=2, nums=[1,2,3]）。
  「range は終端を含まないから +1 が要るはず」という推論が、この学習者では高確率で外れる。
  推論を信用させず、機械的な検算に置き換える。
- `reference/sliding-window-template.html` に「境界の検算」節を追加。対応表を常時参照できるようにした。
- 次セッション冒頭で、この検算が習慣化したかを確認すること。定着していなければレッスンを1本これに割く価値がある。

**関連:** [[0001-hashable-keys]] [[0002-left-monotonicity]] — 「詰まるのは言語仕様の側」という観察の、
より具体的な特定。言語仕様一般ではなく**境界指定**が真犯人だった。

**副次的な発見（②の効果検証）:**
- 演習前に素朴解を声に出させたところ、前半（`O(n×k)` の導出）は正確、
  後半（なぜ O(n) に落ちるか）が曖昧だった。そして**曖昧だった箇所とバグの位置が一致した**
  （「入ってくる1個」を名指しできず、`nums[left]` という窓の内側の要素を足していた）。
- 発話の曖昧さが実装バグを予測する、という直接証拠。本人が「brute force を先に言う意味があるのか」と
  疑問視した直後だったため、説得材料として非常に有効だった。**②は継続する。**
