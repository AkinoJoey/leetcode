# 実装は追いついた。説明の精度が追いついていない

424 を白紙から自力で完答。コードは完全に正しく、境界エラーもゼロ。
`is_invalid` の導出（[[0007-deriving-is-invalid]]）は1回のレッスンで獲得できたとみなせる。

**しかし⑥のコメントに、2セッション連続で誤りが出た。**

| | 実装 | 説明（②⑥） |
|---|---|---|
| Lesson 04 時点（問題3） | 正しい | 「各要素は最大**1回**」→ 誤り |
| Lesson 05 時点（問題424） | 正しい | 空間 `O(min(1, 26))` → 誤り |

**Evidence（今回の3点）:**
1. 空間 `O(min(1, 26(A-Z)))` — この式は文字どおり計算すると **1**。
   問題3で教えた `O(min(n, 文字種))` の形を、対応しない問題に**形だけ流用**した。
   ただし添えた日本語（「キーは1〜26個」）は正しい。**日本語は合っていて式が誤り**＝前回の逆パターン。
2. `max(counter.values())` の **O(26) 走査に言及なし**。Lesson 05 のドリル6で明示的に扱い、
   「黙って O(n) と言うと突っ込まれる」と警告した箇所そのもの。**レッスンで名指しした点が翌回に落ちた。**
3. ②の素朴解「出現した文字の種類 > k になるまで数える」は誤り。
   **種類数と置換回数を混同**しており、これは 424 で最初に詰まった `counter[char] > k` と同じ誤った模型。
   コードは正しく書けているのに、**②には古い模型が残っている。**

**Implications:**
- 実装力と説明力が乖離し始めた。ミッションの定義（「考えを声に出しながら解ききる」）では、
  **説明の精度が成果物そのもの**。ここは実装と同格に扱う必要がある。
- 特に3が重い。正しいコードを書いた直後に誤った素朴解を書いている＝**自分が何を実装したのかを
  言語化できていない**。コードが動いた時点で理解を確認したことにしない。
- 対処：⑥を自由記述にせず**採点基準（rubric）付きの穴埋め**にする。
  時間・空間・素朴解それぞれに「言うべき要素」を固定し、欠けを自分で検出できるようにする。
- 空間計算量の型が未獲得。`O(min(n, 文字種))` を idiom として暗記しており、
  **状態が持ちうる最大要素数から導く**手順を持っていない。導出手順を与えること。

**うまくいったこと（継続）:**
- `⚠ いちばん自信のない行` が**初回から機能した**。挙げたのは `while` の条件式で、
  まさに前回詰まった核心。[[0006-amortized-gap]] を受けた形式変更（「なし」禁止）は正解だった。**維持する。**
- `# valid とは:` を最初に書かせる指示も守られ、424 は自力完答。導出手順は定着したとみなす。
