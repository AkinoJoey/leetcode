## ③：詰まりは6問連続。ただし今回の形は「根拠の2要素のうち片方」

## 核心：③を書かなかった枝が、コードで壊れた

実装のバグは3つ。**すべて境界の等号**で、アルゴリズムは初回から正しかった
（[[0004-off-by-one-dominant]] の「概念 ≫ 境界」がこの型でも再現）。

| # | 誤 | 正 | 症状 |
|---|---|---|---|
| a | `nums[l] < target < nums[mid]` | `nums[l] <= target < nums[mid]` | 区間の左端にある target を落とす |
| b | `nums[mid] > target > nums[r]` | `nums[r] >= target > nums[mid]` | **恒偽**。右半分を一度も見ない |
| c | `if nums[l] < nums[mid]` | `if nums[l] <= nums[mid]` | `l == mid` で else に落ち、前提が壊れる |

**(b) が本命。**`else` 側はソート済みなのが `[mid, r]` なので `nums[mid] <= nums[r]` が成り立っている。
そこに `nums[mid] > target > nums[r]` と書くと `nums[mid] > nums[r]` を要求することになり、**常に偽**。
不一致 8178/20000 のうち大半がこれ。

なぜこうなったか。**③を左枝（`nums[l] <= nums[mid]` の側）でしか書かせなかったから。**

- ③段2で書いたのは「区間 `[l, mid]` に target が**存在しない**条件」
- `else` 側のコードで必要なのは「区間 `[mid, r]` に target が**存在する**条件」
- **主語の区間も、条件の向きも、両方反転する。**書いていない側は、書いていないなりに壊れた

[[0012-bound-not-value]] と [[0022-the-picture-shows-what-was-not-called]] で
「**③が一般形で書ければ、コードの分岐は自動的に決まる**」を2回確認した。
今回それが成り立たなかったのではなく、**前提が満たされていなかった**：

> **③が分岐を決めるのは、③を全ての枝について書いたときだけ。**
> 片側だけ書いた③は、片側だけ正しいコードを生む。

**教える側の失敗。**私は Lesson 16 で「`else` 側もまったく同じ手順を右区間に適用するだけ」と**言った**。
言ったが、**書かせなかった**。NOTES 既出の「警告は知識になるが習慣にはならない」の再発で、
今回は警告ですらなく手順の省略だった。

→ **処方：分岐が対称なとき、対称形は「同じ」と言わずに書かせる。**
`binary-search-template.html` の型Cに、③を**左枝・右枝の2欄**で書く形を入れる。

### (b) は③と照合すれば検出できた

③には「ソート済みなので両端が下限と上限を与える」と書いてある＝`nums[mid] <= nums[r]` を知っている。
なのにコードは `nums[mid] > nums[r]` を要求する式になっていた。
**自分が③で書いた事実と、コードの条件式が矛盾している。**
[[0013-two-kinds-of-discard]] の「主張と実装の不一致」の新形——今回は**説明と実装が論理的に矛盾**していた。
