# 詰まったのはアルゴリズムではなく、変数の役割だった（875. Koko Eating Bananas）

2026-08-04〜05。Lesson 17（型D・答えを二分探索）の導入。
**レッスンを読んだあと、学習者の第一声は「問題文の意味が全然わからない」だった。**
そこから⓪に着手するまでに**6往復**。中身は一度も二分探索の話ではなかった。

## 何が起きたか

詰まりは3層あり、下に行くほど深かった。

| 往復 | 学習者の発言 | 実際の誤解 |
|---|---|---|
| 1 | 「問題文の意味が全然わからない」 | ルール（1時間1山）が読めていない |
| 2 | 「全部1回で食べ切れるから1?」 | **余った時間を次の山に使えない**を読み落とし |
| 3 | 「`max(nums)` にして全部1回で食べきれば良いんじゃない?」 | **何を最小化するのかが見えていない** |
| 4 | 「必ず4回必要だからだ。`n` は必ず最小値」 | **`k` を時間だと思っている**（単位の混同） |
| 5 | `6+3+5+1+4=19`（`h = 5` を `k` に代入） | **`h` と `k` を入れ替えた** |
| 6 | 「30本を1時間で食べきるには？」→「5」 | 同上。`k` を山の数だと思っている |
| 7 | 「それは `h` によるでしょ?」 | **正しい直感**（答えの `k` は `h` に依存する）を、狭い問いに誤適用 |

## 核心：最適化問題は、変数が2種類ある

型A〜Cの問題文は変数が1種類だった——`nums` と `target`。**どちらも与えられるもの**で、
役割を取り違えようがない。875 で初めて、**役割の違う2つの数**が同時に出てきた。

> - `h` ＝ **守るべき制約**。超えてはいけない。動かせない
> - `k` ＝ **こちらが決めるパラメータ**。最小化したい対象

学習者は 5〜6 往復目で **`h = 5` を `k` に代入して計算していた**。
計算そのものは正確（`ceil` も合っていた）。**数式は扱えるのに、どの数を代入する場所なのかが決まらない。**

**型Dの本体はこの区別だ。**「答えを二分探索する」とは、
**最小化したい変数を探索対象に据え、制約を述語の中に押し込む**こと。
`ok(k) = (hours(k) <= h)` という式は、まさに **`k` が探索対象・`h` が制約**であることの宣言になっている。
この式が読めないのではなく、**この式のどちらが動く数かが読めない**状態だった。

## 私の失敗：問題文が読めるかを確認しなかった

Lesson 17 では罠を先回りして潰していた——`piles.sort()` が無意味なこと、
単調性は「厳密に減る」でなく「増えない」で足りること、`hi` は「大きめ」ではなく `ok(hi)` の証明が要ること、
`math.ceil` の浮動小数。**そのどれも、今日は一度も問題にならなかった。**

[[0015-preconditions-are-invisible]] と同じ構造の失敗。
私は「問題文は読める」を**前提として名指しせずに**レッスンを設計していた。
⓪で前提を名指しさせておきながら、自分の前提を名指ししていない。

→ **処方：新しい型の1問目は、問題文の理解確認から始める。**
具体的には「**この問題で、与えられる数と、自分が決める数はどれか**」を1問聞く。
`piles.sort()` のような解法の罠より上流にある。

## 効いた介入と、効かなかった介入

- **効かなかった：表を出す**（`k = 1..100` の時間と ✓✗ の一覧）。3往復目に出したが、
  次の発言が「`n` は必ず最小値」だった。**表は「読めている人」にしか効かない。**
- **効かなかった：偶然の一致を放置した**。例1は `n = 4` と答えの `k = 4` が一致する。
  学習者はここを掴んでしまった。**最初の例が偶然を含んでいないかを確認すべきだった。**
- **効いた：単位を名指しする**。「`4` は速さ（本/時間）であって、時間でも回数でもない」。
- **効いた：極小の例で1回だけ答えさせる**。`piles = [1, 3]`, `h = 2` → `k = 3`。**即答**。
  6往復のあと1往復で通った。**`n = 2`、`h = 2`、答え `3` と3つの数が全部違うので、取り違えようがない。**

→ **処方：理解が詰まったら、登場する数がすべて相異なる最小例を作る。**
偶然の一致（`n` と答え、`h` と `k`）を排除した例は、それ自体が診断器になる。

## 学習者の直感は正しかった

7往復目の「それは `h` によるでしょ?」は、**問題全体としては完全に正しい**
（`h = 5` なら答えは 30、`h = 6` なら 23）。私の問いが狭すぎただけだった。
**間違いに見えたものが、実は正しい一般化だった**——ここを「違います」で潰さなかったのは良い判断。
学習者が黙らずに反論できていることは、33 の「切れ目とは何か」と同じく good
（[[0024-the-other-branch-was-never-written]]）。

## 一問一答の規則を、質問の側にも広げた

セッション冒頭、私は **retrieval（33 の `⚠`）と進捗確認（153/875）を同時に投げた**。
学習者から「1つずつにしない? 何を答えて良いのかわからなくなるし、**両方とも間違っていた場合に指摘が散らばる**」。

08-02 に自分で決めた「返すのは常に1点だけ」を、**聞く側で破っていた**。
→ **規則を一般化：私が一度に投げる問いは常に1つ。種類の違う問い（診断／事務連絡）を混ぜるのも2つに数える。**
返す側が1点なら、聞く側も1点でなければ対応がつかない。

## 実装前パート：③は「わからない」から両枝そろうまで行った

③は初回**空欄（「わからない」）**。ここから6往復の足場で組み上がった。効いた問いの列：

1. 「`ok(mid)` が True ＝ 間に合った。`mid` より大きい `k` は答えになりえるか」→ 即答「ならない」
2. False 側は再び「わからない」→ 「`mid` 自身は答えになりえるか」に割る
3. 「`hours(mid) > h` が確定している `mid` を返したら条件を満たすか」→「満たしていない」
4. 「`mid` より小さい `k` は?」→ **「答えになりえる」（誤答）**
5. 「速さを遅くしたら時間は増えるか減るか」→「増える」→ 言い直させて反転

**4→5 が今日いちばん効いた形。**誤答をその場で否定せず、
**その誤答と矛盾する事実を1つ答えさせて、自分で言い直させた。**（[[0024-the-other-branch-was-never-written]] の定型介入と同型）

そして書き直した③は**両枝そろったが、根拠が両方「最小の整数 k を求めたいから」**だった。
ここを1問（「小さい側を消す根拠はそれか」）で詰めて到達したのが本質：

> **True 側の根拠は最小性、False 側の根拠は単調性。同じ理由で両側を消せることはない。**

33 の `else` 枝が壊れたのも、**片方の根拠しか持っていなかったから**だと言える。
[[0024-the-other-branch-was-never-written]] の「両枝を書かせる」処方は正しかったが、
**書かせるだけでは足りない——根拠が枝ごとに違うことまで確認させる。**

⓪では「単調性を保証しているのは**問題文**」と書いていた。
→ 「いま使った『`k` を小さくすると時間が増える』は問題文に書いてあるか」で1往復で反転。
**型Dの⓪は書き写しでは通らない**（型A〜Cは通った）。★も「最小の整数 `k`」だけだったので、
「`k = 1` はどんな入力でも最小の整数だが」で制約が補われた。

## 実装：③は正しいのに、③に無い行で壊れた

学習者は途中で手が止まり「解けなかった」と申告。提出されたコードの誤りは4つ。

| # | 誤 | 正 | 種類 |
|---|---|---|---|
| a | `sum(piles) // mid` | `sum(-(-p // mid) for p in piles)` | **述語の中身** |
| b | `if eating_time > 8` | `> h` | 例の値のハードコード |
| c | `hi = mid + 1` | `hi = mid` | ③との不一致 |
| d | `while lo <= hi` | `while lo < hi` | 無限ループ |

**(a) が本命で、これは新しい壊れ方だ。**c・d は [[0004-off-by-one-dominant]] の境界（既知の再発）、
b は写し間違い。しかし **a は③にも★にも⓪にも現れない行**で壊れている。

- 型A〜Cでは、判定は `nums[mid] == target` のように**問題文が与える比較**だった
- 型Dでは、**述語の中身も自分で書く**。`hours(k)` は⓪でも③でも一度も式として書いていなかった

> **③が保証するのは「どちらの半分を消すか」だけ。「間に合うか」の計算が正しいことは、③のどこにも書いていない。**

`sum(piles) // mid` は「山の区切りを無視して合計を割る」＝**捨てた余力を数えない**モデル。
`piles=[3,6,7,11]`, `mid=4` で **6（誤）対 8（正）**。
学習者は「27 ÷ 4 は 6 でしょ」と算数を主張した——**算数は正しく、モデルが違う**。
枠の総量で見せて解決（`4+8+8+12 = 32`、`32/4 = 8`、無駄 5本 = 32−27）。

**レッスンで警告済みだった。**第1節の追記に「`sum(piles) / k` で見積もると
切り上げの分だけ短く出て答えを間違えます」と太字で書いてある。**読んだ上で踏んだ。**
NOTES 既出「警告は知識になるが習慣にはならない」の再発。

→ **処方：型Dでは、⓪③とは別に「述語を式で書く」欄を1つ立てる。**
③（消える区間）と述語（間に合うかの判定）は**別の成果物**であり、③が正しくても述語は壊れる。

### `ceil` は「なぜ `-` を使うのか」を聞かれた

`-(-p // k)` を提示したところ「**なぜ `-` を使う?**」。用語で止まらず聞けている（33 の「切れ目とは?」と同じ good）。
数直線を出して `//` が**常に左に丸める**ことを示し、`ceil(x) = -floor(-x)` まで降ろした。
**Python の裏技ではなく床関数と天井関数の関係**だと言えたのが効いた。

## `h` と `k` の混同は、実装前パートでも再発した

`lo = 1` の根拠を聞いたとき、答えは「**0時間以内という単位はないので1から始まる**」。
**`lo` は速さ（本/時間）なのに、また時間として答えている。**
→ 「`piles = [3]` を1時間に0本のペースで食べたら何時間で終わるか」→「終わらない」で解決。
**この混同は1セッション内で3回出た**（`k` を時間と誤認 → `h` を `k` に代入 → `lo` を時間と誤認）。

## 回収したもの

- **`⚠` が実際の詰まりと一致した。**学習者が挙げたのは
  `eating_time = sum(-(-p // mid) for p in piles)`——**まさに本命のバグ (a) の行**。
  33 では `⚠` を答えられずに終わっていた。**「どこが危ういか」を自分で当てられるのは、
  面接で「ここは確認させてください」と言えること**だと伝えた。
- **⑥は名指し2種類が初回で通った**（率を作る行 ＋ 1回のコストを作る行）。
  `O(n log m)` も素朴解の `O(n × m)` も正答。空間 `O(1)` も正答。
  → 補足として**ジェネレータ式と角括弧の差**（`sum([...])` なら空間 `O(n)`）を渡した。

- **今日の詰まりはレッスンの設計では防げなかった。**問題文の理解も、警告済みの罠を踏むことも、
  対話でしか測れない——**レッスンは読み物であって、診断器ではない。**
