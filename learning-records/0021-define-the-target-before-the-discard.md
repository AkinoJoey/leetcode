# ③の前に「何を探しているか」を確定させる／`⚠` が初めて急所に当たった

35. Search Insert Position（型Bの1問目）。コードは一発で正解、`bisect_left` と完全一致
（ランダム2万件、重複ありでも0件不一致）。**詰まったのは実装ではなく③で、3往復かかった。**

## ③：同じ誤りを3回繰り返した

設問は「`nums[mid] >= target` のとき消える区間」。3回とも **704 側の枝**（`nums[mid] < target`）を答えた。

| 回 | 回答 | 何が起きていたか |
|---|---|---|
| 1 | `nums[left..mid-1]`。この区間は target より小さい | 枝の取り違え＋区間が1つずれ |
| 2 | （同上、言い換え） | 図を出す前。反例 `[1,3,3,3,5], t=3` で答え（添字1）を捨てることを提示 |
| 3 | `nums[mid+1..right]`。mid より大きい添字なので最小になれない | **通過** |

### 原因は2つの既知の型の合流

- **形の流用**（[[0018-loop-start-not-constant]]）：704 で慣れた「小さい側を捨てる」をそのまま持ってきた。
  前問からの持ち込みの6例目。**直前に完答した問題ほど流用が強い。**
- **主語のすり替え**（[[0017-subject-of-the-claim]]）：介入の2問目
  「`nums[mid+1..right-1]` にそれはあるか」への回答が「**あるかもしれないし、ないかもしれない**」。
  これは「**条件を満たす要素**があるか」への正答であって、「**答え**があるか」への答えではない。
  ③で毎回起きているのはこれ。

## 突破したのは ✗/✓ の列

配列の値ではなく「`nums[i] >= target` か」の真偽列を描いた。

```
添字     0    1    2    3    4
nums     1    3    3    3    5
>= 3 ?   ✗    ✓    ✓    ✓    ✓      昇順なら ✗…✗✓…✓ で、混ざらない
                   ↑ mid            答え = ✓ が始まる場所
```

図を出した直後、本人から

> 「というか `nums[mid] >= target` って答えが target の範囲だから捨てちゃだめなんじゃない？」

**教える前に自分で言った。**「抽象的な基準は、目で見えるものに変換する」の**6勝目**
（インデント→⑥／格子→③／台帳→前処理／更新行→率／今回は真偽列→③）。第一選択の介入として不動。

## 処方：③の前に「探索対象の定義」を書かせる

3往復のうち最初の2往復は、**答えの定義が曖昧なまま③を書こうとしていた**ことが原因。
本人の初回の言葉は「target と同じ、**あるいは** target が入る場所」——2つに見えていた。

> **型Bでは、③より前に「探しているのは `nums[i] ⚹ target` となる（最小／最大）の `i`」を一文で確定させる。**
> 不等号1つと、最小か最大か。これが埋まるまで③には進まない。

埋まった瞬間（「`nums[i] >= target` となる最小の `i`」）から先は1往復で通った。
704 との本当の違いはここ——**探索対象の定義そのものが違う**（`== target` の `i` vs 境界）。
「`return mid` が使えない」は結果であって、原因ではない。

## ⑥：照合ルールは2回連続で機能。ただし枝が片方

> 「ループの度に半分ずつ範囲を狭めることができている（`l = mid + 1`）ので O(log n)」

[[0020-the-rate-must-be-in-the-code]] の処方（量を言ったら行を名指し）が**2回連続で作動**。
704 の `l += 1` 事件の再発なし。

ただし名指しは `l = mid + 1` の側だけ。**`r = mid` も半分にしている**
（範囲 `r - l` が `mid - l ≈ (r-l)/2` になる）。しかも `mid` を残すぶん、
半分になることが**見えにくいのはこちらの枝**。→ 「両方の枝を指す」を次回の観察項目に。

空間は正答（`l, r` の2つ、入力に依存しない）。

## `⚠`：3回ぶりに急所へ的中。条件変更が効いた

挙げたのは **`return r`**——「target が在る場合と無い場合の両方で、収まる添字が `r` になるか迷った」。

- 18：直したばかりの行（摩耗）／704：`while l <= r`（妥当だが急所でない）→ 2回連続で失中
- [[0020-the-rate-must-be-in-the-code]] で条件を「危なそうな行」→「**今日いちばん自信のない判断をした行**」に変更
- **変更後の初回で的中。** しかも本当にこの問題の要（型Aと型Bを分けている行）。条件変更は成功とみなす。

回答：`while l < r` で抜けた時点で `l == r` なので `return l` と `return r` は同一。
不変条件が「`l` より左は全部 `< target` / `r` 以降は全部 `>= target`」なので、
両者が出会った1点が境界の定義そのもの。`target` が全要素より大きければ `l == r == len(nums)` で末尾挿入。
**`l == r` を保証しているのは `while l < r` という決め事**——三つの決め事の連動がここにも出る。

## Implications

- 型Bは**実装より定義**が難所だった。278（配列なし）でも同じ手順を要求する：
  ⓪で「何がソートされていれば二分探索できるか」＋「探しているのは `isBadVersion(i)` が ___ となる最小の `i`」。
- 冒頭 retrieval 2問（11 の③／704 の半分の行）は**今回未実施**（課題提出から入ったため）。
  storage の計測が1回飛んだ。**次セッション冒頭で必ず実施**。11 の③は3セッション連続で未回収。
- ③の3往復は減点ではない。**3回とも正直に書いて、図が出た瞬間に自力で反転した。**
  取り繕いがないので decay と誤解の形が両方見えている。
