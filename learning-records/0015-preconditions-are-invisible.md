# 16 未完。欠落は `nums.sort()` の1行だけ／「ソートは必須ではない」の過剰適用

16. 3Sum Closest に40分かけて未完。**バグはロジックに1つもなかった。**
欠けていたのは `nums.sort()` だけで、それを足すと全通過する。

```
LeetCode の「答えは一意」制約を満たすランダム入力 7458 件
  提出コード          : 2641件 失敗 (35%)
  sort() を1行足した版 : 0件 失敗

[-1,2,1,-4], target=1 → 提出 -1 / 正解 2
```

両ポインタの動かし方、`min_diff` の更新位置（移動の**後**に置きつつ移動**前**の `three_sum` を使う）、
`float('inf')` の初期化——すべて正しい。

## 合格点：`return` の判断（LR-0014 の検証点(b)）

`else: return three_sum` は**正解**。16 は「最も近い和を1つ返せ」なので差 0 は即最適。
15 で `break` を書いた（167 の文面の持ち込み）のと同じ判断を、今回は外側の問題文から正しく引き直している。
**「内側ループの止め方は外側の問題文が決める」は定着した。**

なお ⑥ は今回未提出のため、検証点(a)（`[時間3]` に掛け算と書けるか）は**未回収**。次回に持ち越す。

## 中心：前提は目に見えないので、最後まで疑われない

40分が溶けたのは、探す場所が最初から違ったから。

- **アルゴリズムはコードに書いてある。前提は書いていない。**
- しかも 16 は前提を落としても**落ちない**。例外も無限ループも出ず、それらしい数字を返す。
  → 「ロジックのどこかが微妙に違う」と読んでしまう。

デバッグ順序として渡した規則：**ロジックより先に前提を疑う**（確認10秒 vs 追跡40分、安いほうから）。

## 解決策：③を一般形で書くと、前提が文の中に現れる

16 の③を一般形で書くと：

> `three_sum < target` のとき、`j` を固定して `k` を減らすと、**ソート順より** `nums[k'] ≤ nums[k]`
> なので和はさらに小さくなり、target からさらに遠い。よって `(j, k')` は**いま記録した値を超えられない**。

**「ソート順より」が③の中から出てくる。**この一句を消すと③は成立しない。

[[0012-bound-not-value]] で「③が正しく書ければ**コードの分岐**は自動的に決まる」と確認した。
今回はその続き：**③が正しく書ければ、コードの前処理も自動的に決まる。**
③は正しさの説明であると同時に、**実装の生成規則**として2回連続で機能している。

## 教材起因の疑い：強調した否定が過剰に効いた

[[0012-bound-not-value]] で「**ソートは③の必須条件ではなく、上限を得る手段のひとつ**」を
11 の詰まりを解くために強く打ち出した。これ自体は正しいが、**逆方向（いつ要るのか）を並べて言わなかった**。

NOTES の「**強調した語彙は隣接する誤概念を引き寄せる**」（[[0011-discard-rate-vs-discard-reason]]）の
新しい形。今回は語彙ではなく**否定**が引き寄せた。15 では書けていた `sort()` が 16 で落ちている以上、
「知らない」ではなく**一度打ち消された**と見るのが自然。

→ `two-pointers-template.html` の当該節を「ソートは必須ではない」から
**「上限はどこから来るか ＝ ソートが要るかの判定」**に改題し、要る側・要らない側を**同じ枠内に並置**した。
判定規則は一文：**③が「値の大小」に依存しているならソートが要る。添字や対称性で済むなら要らない。**

## 介入：⓪前提 の欄（2行必須）

```
⓪ 前提（この解法が入力に要求する条件）: 昇順にソート済みであること
   保証している行: nums.sort()
```

**2行目が本体。**前提は書けても保証する行を名指しできないなら、**その行はまだ存在していない。**
これは [[0013-two-kinds-of-discard]] の「主張と実装の不一致」に対する、
警告ではなく**照合が強制される形**での対処。167 は「—（問題文が保証）」と書けるので、
問題文が保証する場合と自分で書く場合の区別も同じ欄で取れる。

## Implications

- **教材の否定形は、肯定形とペアで置く。**「X は必須ではない」だけを置くと、
  X が実際に必要な場面で落ちる。次に否定を書くときは、必ず同じ節に「では、いつ要るのか」を並べる。
- ⓪の検証点：16 の再提出で（a）⓪が2行で埋まるか、（b）`[時間3]` に**リセット＝掛け算**と書けるか
  （LR-0014 からの持ち越し）、（c）`sort()` により `[空間]` が `O(1)` にならないと気づけるか。
  (c) は 15 で名指ししたまま**唯一未修正**だった空間欄の再検査でもある。
- 40分の詰まり自体は悪い兆候ではない。**バグがロジックにないと分かれば、次からは10秒で終わる種類の詰まり。**
