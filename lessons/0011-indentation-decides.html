Lesson 11 · 計算量

掛け算か足し算かは、
インデントで決まる

3回連続で同じ場所に止まっています。原因は私の説明の抽象度なので、目で見えるものに置き換えます。

これまでの説明が悪かった

私はこう書いていました——「内側ポインタが持ち越されるか、リセットされるか」。 これは正しいのですが、頭の中で追跡しないと判定できません。 だから 15 でも 16 でも、その場では出てこなかった。

判定は追跡しなくてもできます。初期化行がどこに書いてあるかを見るだけです。

2つのコードを並べる

どちらも「外側ループの中で内側ポインタを動かす」コードです。違いは1箇所しかありません。

424. Character Replacement — O(n)

left = 0                          ← for の外
for right in range(len(s)):
    ...
    while is_invalid():
        left += 1
16. 3Sum Closest — O(n²)

for i in range(len(nums)):
    j, k = i + 1, len(nums) - 1   ← for の中
    while j < k:
        ...

内側ポインタの初期化行が、外側ループの外にあれば足し算。中にあれば掛け算。

インデントを見るだけです。left = 0 は左端に、j, k = ... は1段下がっている。 これが計算量そのものです。

なぜそれで決まるのか

424（外にある）16（中にある）
内側ポインタは left は一度も戻らない j, k は毎回 i+1, n-1 に戻る
内側の総仕事量 プログラム全体で合計 n 回
（0 から n まで進むだけ）		 1周ごとに n 回
（毎回ゼロからやり直す）
数え方 外側 n + 内側 n ＝ 足し算 外側 n × 内側 n ＝ 掛け算
結論 O(n) O(n²)

「初期化行が外にある」＝「前の周の続きから始まる」＝「戻らない」。 戻らないものは、全体でも n 回しか進めません。だから外側の回数と足せる。
「初期化行が中にある」＝「毎周ゼロから」。ゼロからなら毎回フルに走りうるので掛ける。

面接での言い方（これを丸ごと言えば通ります）

「j, k の初期化が外側ループの内側にあるので、毎回リセットされます。 償却できないため掛け算で、n × n = O(n²)。
ソートの O(n log n) はこれに吸収されます。」

「外側と内側でループが回るから O(n²)」は、424 でも同じことが言えてしまうので 根拠になりません。面接官は必ずそこを突きます。

判定ドリル

コードだけを見て、足し算か掛け算かを答えてください。追跡しないこと。インデントだけ見る。

3. Longest Substring Without Repeating Characters
left = 0 / for right in ...: /     while s[right] in seen: left += 1

足し算。left = 0 が for の外。left は戻らないので全体で n 回 → O(n)。

18. 4Sum（の内側2重）
for i in ...: /   for j in ...: /     l, r = j+1, n-1 /     while l < r:

掛け算。l, r の初期化が for j の中。よって n² × n = O(n³)。次の問題です。

1004. Max Consecutive Ones III
left = zeros = 0 / for right in ...: /     while zeros > k: left += 1

足し算。初期化が外。while が何重に見えても、left が戻らない限り総量は n。

この判定法が壊れるのはどんなときか。

この判定が効くのは「初期化行が外 ⇒ 単調に進むだけ」という含意があるからです。 ループ内で left を減らす実装があれば、外に書いてあっても足し算は成り立ちません （Lesson 02 の左端の単調性＝ LR-0002）。
逆に言えば、単調性さえ確認すれば、あとはインデントだけで判定してよい。

おまけ：`⚠` に挙げた行の話

if curr_diff < min_diff を挙げたのは正しい判断でした。危険なのは式ではなく時制です。 

curr_diff = abs(target - three_sum)   # ← この時点の j, k
if three_sum < target:
    j += 1                            # ← j が動く
...
if curr_diff < min_diff:              # ← ここでの nums[j] は curr_diff の j ではない
    best_sum = three_sum              # ← three_sum も移動前の値。だから正しい

curr_diff と three_sum を移動前に確定させているので整合しています。 ただし「更新をポインタ移動の後に書く」形は、後から1行足したときに壊れます。 面接で言うなら「更新は移動前の値を使っているので、この2行は動かせません」。

より安全な形（好みの問題。今のままでも正しい）

更新を移動の前に置くと、時制の依存が消えます。 

three_sum = nums[i] + nums[j] + nums[k]
if abs(target - three_sum) < min_diff:    ← 先に記録
    min_diff = abs(target - three_sum)
    best_sum = three_sum

if three_sum < target:   j += 1           ← あとで移動
elif three_sum > target: k -= 1
else: return three_sum
