Lesson 14 · 新しい型：binary search

率であって、理由ではない

Lesson 07〜08 で「two pointers は log n ではない」と強く否定しました。今日はその否定形の相方——では、いつ log n になるのか。

まず思い出す（前々回より前の問題から）

11. Container With Most Water。短いほうの板を動かすとき、捨てた組について言えることは？

捨てているのは値ではなく上限です（LR-0012）。 「小さいから捨てる」ではありません——その板を含む組は全部まとめて、今の面積を超えられないと証明できるから捨てる。 これが「捨ててよい理由」です。今日は、この理由のとなりにあるもう一つの量を扱います。

two pointers も binary search も、毎回何かを捨てます。捨てる理由はどちらも同じ——ソート順による証明です。
違うのは率。two pointers は毎回1個、binary search は毎回半分。
log n を生むのは理由ではなく率です。

1. 同じ理由、違う率

LR-0011 で、 「捨てるから速い」という言い方が雑すぎることを扱いました。伏線をここで回収します。

捨てる理由1回あたり捨てる量回数
two pointersソート順による証明1行 or 1列（＝定数個の"組"ではなく、残り n 個中の 1個）n
binary searchソート順による証明残っている範囲の 半分log n

理由の欄はまったく同じです。だから「ソート済みだから log n」は誤りになります。 ソート済みは捨てる権利を与えるだけで、速さは与えません。 速さを決めるのは、その権利を使って一度にどれだけ捨てるかのほうです。

Lesson 07〜08 との接続

あのときのギャップ論法は「two pointers では、ポインタが毎回1つずつしか動かないので、 合計 n 回で終わる＝ log にはならない」でした。 今日の言い方に直すと：率が 1/n だから線形。 否定形（Lesson 07）と肯定形（今日）は、同じ一本の軸の両端です。

なぜ「半分」が log になるのか

捨てたあとに残る個数だけを、上から書き下します。

ステップ残っている個数
0n
1n / 2
2n / 4
kn / 2k
終了条件n / 2k = 1　⟹　k = log₂ n

数えているのはステップ数 k であって、要素数ではありません。 log が出てくる場所は常にここ——「何回で 1 になるか」を数えたときだけです。

n = 1024。毎回ちょうど半分を捨てるとき、範囲が 1 になるまで最悪で何回かかりますか（数字だけ）。

10。210 = 1024 だから。 面接では「n が10億でも30回ちょっと」と言えると強い—— log の実感が伴っている合図になります。

二分探索が O(log n) になる根拠として、いちばん正確なのは？

一定の割合です。「ソート済みだから」は two pointers にも当てはまってしまうので、 log n の説明になりません（LR-0016 と同じ検査： その説明は、別の解法にも当てはまってしまわないか）。 「早く見つかれば」は最良の話で、計算量は最悪を言います。

2. 何を捨てたのか、名指しする

③（捨ててよい理由）の主語は消えた組でした （LR-0017）。二分探索でも同じです。主語は消えた区間。

二分探索の不変条件は、たった一文です。

答えが存在するなら、それは常に [left, right] の中にある。

毎回の更新は、この一文を壊さないまま範囲を狭める操作です。 nums[mid] < target なら、ソート順より nums[left..mid] は全部 target 未満—— だから left = mid + 1。捨てたのは「mid 以下の添字の区間まるごと」です。

③ の書き方（two pointers と同じ手順）

先に集合を名指しする：「捨てるのは left..mid の区間です」。
次に理由：「ソート順より、そこは全部 target 未満だからです」。
この順番です。「小さいほうを動かします」だけでは、③ ではなく ② になります。

3. 三つの決め事と、終わることの証明

def search(nums, target):
    left, right = 0, len(nums) - 1      # ← 決め事1：閉区間 [left, right]
    while left <= right:                # ← 決め事2：空になるまで
        mid = (left + right) // 2
        if nums[mid] == target:
            return mid
        if nums[mid] < target:
            left = mid + 1              # ← 決め事3：mid は評価済み。含めない
        else:
            right = mid - 1
    return -1

三つは独立に選べません。閉区間 [left, right] を選んだ時点で、 while は <=（left == right はまだ「1個残っている」状態）、 更新は mid ± 1（mid は今まさに評価したので、範囲に残す理由がない）——と決まります。 一つ変えたら三つとも見直す。

更新を left = mid に変えたとき（他はそのまま）、何が起きますか？

無限ループです。left = 3, right = 4 のとき mid = (3+4)//2 = 3。 left = mid は left = 3 ——何も変わらないまま次の周回に入ります。
ここが二分探索で最も多いバグです。「毎回、範囲が真に狭まるか」を、隣接した2要素で必ず確かめる。 LR-0004（あなたの誤りの最大分類は off-by-one）の、この型での現れ方です。

Python では起きないバグ

C や Java では (left + right) が桁あふれするため left + (right - left) // 2 と書きます。 Python の整数は多倍長なので、この心配は不要です。 面接で聞かれたら「Python では不要ですが、固定長整数の言語では left + (right-left)//2 にします」と答えれば十分。 覚える対象ではなく、聞かれたときの一言として持っておいてください。

4. 前提（⓪）は、誰が保証しているか

LR-0015 の形をそのまま使います。 二分探索の前提はソート済みであること。ただし今回、保証しているのは問題文です ——15 や 18 のように、あなたのコードが sort() して作る前提ではありません。

ここは Python の標準ライブラリも同じ立場を取っています。 bisect モジュールのドキュメントは、 リストがソート済みであることを前提として要求するだけで、確認も並べ替えもしないと明記しています （"assuming that a is already sorted"）。前提は呼び出し側の責任、という設計です。

⑥ への影響（前回の台帳と接続）

Lesson 13 の規則は「⑥は1行目から上から順に読む」でした。 704 では1行目に sort() がありません——だから O(log n) がそのまま残ります。 もし自分で sort() していたら O(n log n) に飲まれ、二分探索した意味が消える。 「ソートしてから二分探索」は、探索が何度も走るときだけ元が取れます。

読むもの

主資料： Python 公式ドキュメント — bisect。 bisect_left と bisect_right が返す「挿入位置」の定義、 とくに二つの関数が保証する分割の条件（左側は全部 < x / 右側は全部 >= x）を読んでください。 今日の不変条件と同じことを、標準ライブラリの言葉で書いたものです。 自分で書く二分探索も、最終的にはこの二つのどちらかに帰着します。
